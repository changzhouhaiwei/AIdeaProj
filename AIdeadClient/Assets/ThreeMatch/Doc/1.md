# ThreeMatch 三消游戏开发文档

## 1. 目标

在 `Assets/ThreeMatch` 目录内制作一套独立的三消玩法原型，效果参考 Royal Match 这类关卡制三消游戏。

当前阶段先完成最基础的关卡初始化能力：

1. 读取 `Assets/ThreeMatch/Level` 目录下的关卡 JSON 配置。
2. 根据配置生成棋盘背景格子。
3. 根据配置生成初始棋子。
4. 在 `Assets/ThreeMatch/ThreeMatchScene.unity` 场景中可以直接运行并看到关卡棋盘。
5. 每完成一部分代码，都在本文档中补充说明，让后续能看懂实现逻辑。

本模块只依赖 `Assets/ThreeMatch` 内的资源、脚本和配置，不参考项目中其他文件夹的代码。

## 3. 场景入口

场景路径：

```text
Assets/ThreeMatch/ThreeMatchScene.unity
```

建议场景中至少包含以下对象：

1. `ThreeGameMgr`：挂载 `ThreeGameMgr.cs`，作为游戏初始化入口。
2. `BoardRoot`：棋盘背景格子的父节点。
3. `ChessRoot`：棋子的父节点。
4. `Camera`：用于显示整个棋盘。

`ThreeGameMgr` 负责选择测试关卡，例如 `level = 1` 时加载：

```text
Assets/ThreeMatch/Level/u_level1.json
```

读取关卡后，初始化顺序应为：

1. `ThreeGameMgr` 加载并解析关卡配置。
2. `ThreeBoardMgr` 根据 `slotInfo` 生成棋盘背景。
3. `ThreeChessMgr` 根据 `pieceInfo` 生成初始棋子。

## 4. 关卡配置说明

关卡文件是 JSON 格式，例如：

```text
Assets/ThreeMatch/Level/u_level1.json
```

### 4.1 基础字段

| 字段 | 含义 | 示例 |
| --- | --- | --- |
| `level` | 关卡编号 | `1` |
| `levelType` | 关卡类型 | `0` |
| `steps` | 可用步数 | `30` |
| `xMax` | 棋盘横向格子数量 | `9` |
| `yMax` | 棋盘纵向格子数量 | `8` |
| `fillType` | 填充类型，当前先保留 | `0` |
| `targetInfo` | 关卡目标信息 | `[[101,36],[0,0],[0,0],[0,0]]` |

### 4.2 坐标规则

配置中的坐标以数组形式出现：

```json
[x, y, ...]
```

含义：

1. `x` 表示列，从左到右递增。
2. `y` 表示行，从下到上递增。
3. 生成到 Unity 世界坐标时，可以按格子大小换算。

建议初期使用下面的简单换算方式：

```text
worldX = (x - (xMax - 1) / 2f) * cellSize
worldY = (y - (yMax - 1) / 2f) * cellSize
```

这样生成的棋盘会以场景原点为中心，方便相机对齐。

### 4.3 slotInfo：棋盘格信息

`slotInfo` 决定哪些位置需要生成棋盘背景。

每条数据格式：

```json
[x, y, slotType, spawnerFlag]
```

当前可按以下含义理解：

| 下标 | 字段 | 含义 |
| --- | --- | --- |
| `0` | `x` | 棋盘列坐标 |
| `1` | `y` | 棋盘行坐标 |
| `2` | `slotType` | 格子类型，`1` 表示可用普通格 |
| `3` | `spawnerFlag` | 是否是掉落生成入口，通常顶部或配置指定位置为 `1` |

当前阶段的 `ThreeBoardMgr` 只需要处理：

1. 遍历 `slotInfo`。
2. 当 `slotType > 0` 时，在对应坐标生成背景格。
3. 背景格使用 `oriPieceObject` 或后续命名为 `boardCellPrefab` 的预制体。

### 4.4 bottomInfo：底层元素信息

`bottomInfo` 通常表示棋盘底层元素，比如草地、泥土、果冻、箱子底座等。

每条数据格式：

```json
[x, y, bottomType, bottomParam, logicX, logicY]
```

当前阶段暂不生成底层元素，只需要保留字段解析能力。后续如果要做关卡目标、障碍物或底层消除，可以从这里扩展。

### 4.5 pieceInfo：初始棋子信息

`pieceInfo` 决定每个格子初始放什么棋子。

每条数据格式：

```json
[x, y, pieceType, layer, logicX, logicY, color]
```

当前可按以下含义理解：

| 下标 | 字段 | 含义 |
| --- | --- | --- |
| `0` | `x` | 棋子所在列 |
| `1` | `y` | 棋子所在行 |
| `2` | `pieceType` | 棋子或障碍物类型 |
| `3` | `layer` | 层级，当前多为 `1` |
| `4` | `logicX` | 逻辑列坐标 |
| `5` | `logicY` | 逻辑行坐标 |
| `6` | `color` | 普通棋子的颜色编号 |

当前已有图片资源对应关系：

| 棋子编号 | 图片 |
| --- | --- |
| `1` | `0001_red.png` |
| `2` | `0002_yellow.png` |
| `3` | `0003_blue.png` |
| `4` | `0004_green.png` |
| `5` | `0005_purple.png` |

注意：

1. `pieceType` 为 `1` 到 `5` 时，可以直接当作普通颜色棋子生成。
2. `pieceType` 为 `101`、`1002`、`9999` 等值时，可能代表特殊元素、目标物或占位类型。当前阶段可以先跳过，或用占位棋子显示，避免初始化流程中断。
3. 部分配置里 `pieceType` 和 `color` 都可用于判断普通棋子。为了简单稳定，第一版优先使用 `pieceType` 选择棋子预制体。

### 4.6 upperInfo：上层元素信息

`upperInfo` 通常表示覆盖在棋子上方的元素，例如锁链、冰层、罩子等。

每条数据格式：

```json
[x, y, upperType, upperParam, logicX, logicY]
```

当前阶段暂不生成上层元素，只保留解析能力。

### 4.7 emptyFillRule：空格填充规则

示例：

```json
[1,100,2,100,3,100,4,100,5,0]
```

可以理解为棋子类型和权重成对出现：

```text
棋子 1 权重 100
棋子 2 权重 100
棋子 3 权重 100
棋子 4 权重 100
棋子 5 权重 0
```

后续当棋盘出现空格时，可以按此权重随机生成新棋子。当前阶段只做初始棋子生成，暂时不需要使用。

### 4.8 spawnerRuleInfo / spawnerRuleAllocation：掉落生成规则

`spawnerRuleInfo` 定义不同掉落规则。

示例：

```json
{
  "index": 0,
  "rule": [1,110,2,100,3,160,4,100,5,0],
  "totalWeights": 470
}
```

含义：

1. `index` 是规则编号。
2. `rule` 是棋子类型和权重列表。
3. `totalWeights` 是总权重。

`spawnerRuleAllocation` 决定哪个生成入口使用哪条规则。

示例：

```json
[0,0,0]
```

可以理解为：

```text
x = 0
y = 0
ruleIndex = 0
```

当前阶段暂不实现掉落，只需要知道这些字段后续会用于补棋。

## 5. 代码职责设计

### 5.1 ThreeGameMgr

职责：

1. 保存当前测试关卡编号。
2. 根据关卡编号加载 `u_level{level}.json`。
3. 把 JSON 解析成 C# 数据结构。
4. 调用 `ThreeBoardMgr` 生成棋盘背景。
5. 调用 `ThreeChessMgr` 生成初始棋子。

建议对外流程：

```text
Start()
└── LoadLevel(level)
    ├── 读取 JSON
    ├── 解析 LevelData
    ├── boardMgr.Init(levelData)
    └── chessMgr.Init(levelData)
```

### 5.2 ThreeBoardMgr

职责：

1. 接收关卡数据。
2. 根据 `xMax`、`yMax` 和格子大小计算世界坐标。
3. 遍历 `slotInfo`。
4. 为每个可用格子生成棋盘背景。
5. 保存坐标和格子对象的对应关系，方便后续棋子定位。

建议字段：

```text
boardCellPrefab      # 棋盘背景格预制体
boardRoot            # 生成出来的格子父节点
cellSize             # 单格间距
```

### 5.3 ThreeChessMgr

职责：

1. 接收关卡数据。
2. 遍历 `pieceInfo`。
3. 根据棋子类型选择对应棋子预制体。
4. 在棋盘坐标对应位置生成棋子。
5. 保存棋子二维数据，后续用于交换、消除、下落。

建议字段：

```text
chessOriList         # 普通棋子预制体列表
chessRoot            # 生成出来的棋子父节点
cellSize             # 单格间距，应和 BoardMgr 一致
```

### 5.4 BaseChess

职责：

1. 表示单个棋子。
2. 记录自己的棋子类型、颜色、棋盘坐标。
3. 后续扩展点击、交换、移动动画、消除动画等行为。

建议字段：

```text
x                    # 当前逻辑列坐标
y                    # 当前逻辑行坐标
pieceType            # 棋子类型
color                # 棋子颜色
```

## 6. 第一阶段实现步骤

### 步骤 1：定义关卡数据结构

新增或写入脚本：

```text
Assets/ThreeMatch/Scripts/ThreeLevelData.cs
```

需要包含：

1. `ThreeLevelData`
2. `SlotInfo`
3. `PieceInfo`
4. `BottomInfo`
5. `UpperInfo`
6. `SpawnerRuleInfo`

由于 JSON 中大量字段是数组结构，Unity 自带 `JsonUtility` 对嵌套数组支持不够方便。实现时可考虑：

1. 使用简单 JSON 库解析。
2. 或先定义和 JSON 完全对应的数组字段结构。
3. 如果项目暂时不引入第三方库，也可以用 `System.Serializable` 配合包装类处理简单字段，再针对数组做转换。

### 步骤 2：加载关卡 JSON

推荐把关卡 JSON 放在 Unity 可读取的位置。当前路径是：

```text
Assets/ThreeMatch/Level/u_level1.json
```

如果运行时直接加载，可以使用：

```text
Resources.Load<TextAsset>
```

但这要求关卡文件放入 `Resources` 目录。另一种方式是编辑器测试阶段通过路径读取文件。

第一版为了快速验证，可以优先做编辑器内路径读取：

```text
Application.dataPath + "/ThreeMatch/Level/u_level" + level + ".json"
```

### 步骤 3：生成棋盘背景

`ThreeBoardMgr` 执行逻辑：

1. 清理旧棋盘。
2. 遍历 `levelData.slotInfo`。
3. 如果 `slotType <= 0`，跳过。
4. 根据 `x`、`y` 计算世界坐标。
5. 实例化棋盘背景格。
6. 设置父节点和局部坐标。

### 步骤 4：生成初始化棋子

`ThreeChessMgr` 执行逻辑：

1. 清理旧棋子。
2. 遍历 `levelData.pieceInfo`。
3. 如果 `pieceType` 不是 `1` 到 `5`，先跳过或生成占位。
4. 根据 `pieceType` 从 `chessOriList` 选择预制体。
5. 根据 `x`、`y` 计算世界坐标。
6. 实例化棋子。
7. 调用 `BaseChess.Init(...)` 保存逻辑数据。

## 7. 第一阶段完成标准

完成后，在 `ThreeMatchScene.unity` 运行应看到：

1. 根据 `u_level1.json` 生成的棋盘背景。

3. 修改 `ThreeGameMgr.level` 后，可以加载不同关卡。
4. 非普通棋子类型不会导致报错。
5. Hierarchy 中生成的棋盘和棋子分别挂在对应父节点下，结构清晰。

## 8. 后续扩展方向

第一阶段完成后，再继续做核心三消玩法：

1. 点击或拖拽两个相邻棋子进行交换。
2. 判断横向或纵向三个及以上同色棋子。
3. 消除匹配棋子。
4. 棋子下落补空。
5. 根据 `emptyFillRule` 和 `spawnerRuleInfo` 生成新棋子。
6. 检查关卡目标 `targetInfo`。
7. 步数减少和胜负判断。
8. 扩展特殊棋子、障碍物、上层覆盖物和底层元素。
